# 交易补偿与库存说明

本文记录当前交易边界，供修改订单、支付、拼团及退款逻辑时核对。

## 下单与库存

- 普通订单创建时校验商品和库存，价格与总金额由服务器确定。
- 默认关闭预占：未付款订单不扣库存。完成迁移并统一启用 `inventory.reservation.enabled=true` 后，普通订单与购物车结算在创建事务中预占可售库存，付款时消费预占并确认销量。拼团仍在付款时扣剩余可售库存。
- 同一支付批次涉及同一商品时，先校验合计数量，避免分别校验通过后出现负库存。
- 无法履约的真实收款进入持久化补偿退款流程。支付渠道侧截止时间与独立支付/退款流水尚未实现。预占功能需手动迁移后启用，旧订单无预占记录时兼容原支付路径。

## 普通待付款订单超时关闭

- `UnpaidOrderExpiryTask` 首次延迟及扫描间隔默认均为 60 秒，每批最多关闭 200 笔。
- `order.unpaid-timeout-minutes` 默认为 30，允许 1 至 10080；`order.unpaid-expiry.enabled=false` 可关闭此任务。
- 条件更新仅匹配普通订单、待付款状态、未记录支付流水和支付时间，且创建时间超过截止时间的记录。
- 关闭只把待付款状态 0 改为已取消 4，保存上一状态 0 和更新时间。启用预占后先锁定订单、核对付款状态，再在同一事务中释放有效预占和关闭订单；关闭写入失败会抛出异常回滚。
- 支付通知锁定订单行，超时关闭使用数据库条件更新。先完成付款的订单不再匹配关闭条件；先被关闭的订单若收到真实成功收款，进入补偿退款。
- 支付页面创建入口与清理任务共用超时窗口和包含截止点的判断。普通订单达到期限后，即使状态仍为待付款，也会返回 HTTP 409，不调用支付宝生成新页面；批次中任一普通订单超时则整批拒绝。关闭后台清理开关不会关闭这项支付入口检查，缺少创建时间的历史记录保留兼容行为。
- 支付入口拒绝后不直接改订单状态或释放库存，仍由主动取消或后台清理事务处理。已有支付流水或支付时间的异常待付款记录同样拒绝再次请求收款。
- 已生成的支付页面不由入口检查撤销，真实签名通知仍按当前订单状态和原补偿流程处理；当前尚未配置支付渠道侧的精确截止时间，不能将入口限制当成渠道关单或迟到收款退款的完整证明。
- 拼团订单不由此任务关闭，继续沿用拼团过期、失败和补偿流程。
- 更新后下次启动会扫描符合条件的历史待付款订单。无预占记录的订单不补库存；有记录的订单按账本状态最多释放一次。

## 发货与签收

- 订单和物流入口共用履约校验，拼团成功后才能发货。
- 退款中、已关闭等状态不能通过物流接口绕过限制。拒绝退款后的履约状态按保存的上一状态判断。
- 物流状态只允许按顺序推进，重复操作在一致状态下保持幂等；取消物流不能替代退款流程。
- 物流写操作按订单、物流的顺序加锁；订单地址只能在待付款或待发货时局部更新。

## 退款与补偿

- 拼团失败先保存应退状态，独立自动退款任务继续处理，支付渠道异常时保留待办并重试。
- 已验签的迟到支付、库存不足等不能履约的收款，同样保存支付信息并进入补偿退款。
- 每笔订单使用稳定退款请求号 `REFUND_ORDER_订单ID`；重复处理沿用同一请求号。
- 无法履约的支付通知先释放仍有效的预占，之后补偿退款不再补库存。未预占、未扣库存的补偿退款同样不补库存。已发货退款也不直接补库存，实物退回后应通过出入库管理验收。
- 已成团后的个人退款不直接使其他成员的团失败。

## 验证边界

服务回归测试覆盖签名、金额、状态、重复支付和补偿分支；超时任务测试覆盖时间窗口、批次限制及失败后继续调度。数据库条件更新仍需真实 MySQL 并发验证，资金处理仍需支付宝沙箱及真实回调链路验证。不要把 Mockito 测试当成数据库锁竞争或支付联调的结果。

## 预占账本与上线顺序

`inventory_reservation` 以订单 ID 为主键，保存商品、数量和状态（1 有效、2 已消费、3 已释放）。扣可售库存、写账本和创建订单处于同一事务。消费只确认销量；释放不确认销量。商品下架不阻止已有有效预占恢复可售数量。

已有数据库先在维护窗口停止后端实例，审查并执行 `src/main/resources/db/migration/V20261023_01__inventory_reservation.sql`，然后统一启用各实例。新库表结构脚本已包含此表，但开关仍默认关闭。存在有效预占时禁止关闭开关启动；启用前未迁移也会拒绝启动。不要混用不同开关配置处理同一数据库。

此脚本只新增表，不自动回填历史订单，也不会由应用自动执行。库存预占不解决恶意囤单或支付对账，已增加每用户有效预占额度，仍需进行真实数据库并发、死锁重试和回滚验证；这不等于已完成多账号滥用防护。

## 每用户预占额度

默认上限为 10 条有效预占订单记录、50 件商品，可使用 `inventory.reservation.max-held-orders` 和 `inventory.reservation.max-held-units` 调整，必须为正整数。额度只统计账本状态 1，已消费和已释放记录不占用额度；旧订单没有预占记录，不纳入这项限制。

普通订单与购物车结算先锁定买家，再开始读商品和创建订单，且使用 READ COMMITTED 事务。后续预占在同一事务中检查按买家汇总的记录数与数量，避免等到买家锁后还读取旧快照。购物车每新增一条预占都会计入本事务后续检查，任一商品超限时整个结算事务失败。付款和释放不增加有效预占，因而可能使检查偏保守，但不能增加分配额度。

这套保护需要真实 MySQL 并发验证，不应将服务调用顺序测试当作实际锁竞争证明。

## 创建订单的请求幂等

普通下单和购物车创建接口接收可选 `Idempotency-Key`。同买家、同入口和同标识映射为商户订单号的前 32 位；创建内容指纹占后 32 位。后端先在 READ COMMITTED 事务内锁定买家，再按买家与订单号前缀查询记录：完全匹配返回已有订单，内容冲突返回 HTTP 409，没有记录才创建。买家锁由事务结束释放，创建失败回滚后同标识可重试。没有请求头的旧调用保留原有行为。

购物车 ID 在生成指纹和实际创建前统一转为正整数、去重并排序，拒绝小数、越界和非正数。同一标识的重试不重新读取已删除的购物车项、不重新计价或预占；返回原批次金额与当前状态。若批次任一订单已处理，`paymentAllowed=false`，前端引导查看已有订单。该字段只是界面提示，实际支付始终重新校验数据库状态。

浏览器为相同待处理内容复用请求标识，购物车支付请求失败后也保留标识。保护范围受当前标签页会话存储与最多 20 个待处理内容的缓存限制；修改内容、存储被清除或使用不带请求头的客户端，仍可能创建新订单。没有新增独立请求账本，因此交易记录及商户订单号不可物理删除或改写；部署时应统一更新处理下单的实例。

本轮测试覆盖映射、冲突、买家与入口隔离、重放时跳过创建和库存、购物车 ID 规范化，以及浏览器响应丢失、支付失败、刷新重试。未连接真实 MySQL 或支付渠道，不代表已验证真实并发事务和支付通知。

## 订单页支付交互

支付确认弹窗通过文本节点显示商品名，避免将商品名拼接为 HTML。支付过程中禁用重复点击；确认取消、准备失败、支付请求失败、缺少支付表单及正常跳转都会释放本次加载状态。支付请求只提交商户订单号，金额继续由服务端计算。HTTP 409 的业务原因由统一请求拦截器展示。

## 人工出入库与库存记录冲销

- 出入库先锁定商品；作废先锁定库存记录，再锁商品。同一商品的库存变动必须检查商品更新恰好影响一行，流水插入、作废或删除失败均抛出异常，由事务回滚。
- 入库增加与作废出库的恢复数量使用整数溢出检查，上限为 2147483647；出库和作废入库不能使可售库存为负。库存为空或负数、有效记录数量非正、状态异常、作废时商品缺失，均拒绝操作并要求核对。
- 删除有效记录沿用先作废再删除的事务流程，作废失败不能继续删除；已经作废的记录不再次变动库存。现有删除功能不是独立审计账本，长期审计仍需另外设计不可删除的记录策略。
- 这些操作只调整 `product.stock` 可售库存，不更改普通订单预占状态。实物、有效预占及可售库存应分别核对，不能将作废出库当成订单退款或释放预占。
- 商品编辑继续保留锁定行中的库存和销量，不接受编辑表单覆盖。更换图片保留旧文件，避免共享引用失效及数据库回滚不能恢复文件的问题；文件清理需独立核对引用并备份。
